## 第25回　API 接口的向后兼容与灰度演进

### 第25回　API 後方互換性と段階的ロールアウト

------

## 中文版

### 引言

API 是外部系统与内部系统之间的 **契约**。
 任何破坏性的 API 变更都会导致调用方出错，影响线上稳定性。
 因此，API 的 **向后兼容** 与 **灰度演进** 是大规模系统重构中的核心问题。

------

### 25.1 向后兼容的原则

1. **新增优于修改/删除**
   - 新增字段安全，删除或重命名字段会破坏兼容性。
2. **保持默认值与可选参数**
   - 确保旧客户端即使不传新参数也能工作。
3. **错误码向后兼容**
   - 新增错误码可以，修改已有错误码含义会破坏兼容性。
4. **版本化机制**
   - 使用 `/api/v1` → `/api/v2` 控制破坏性变更范围。

------

### 25.2 灰度演进（Progressive Rollout）

API 重构时，不可能一次性切换所有调用方。
 👉 **灰度演进策略**：

- **双写机制**：服务端同时写入新旧字段。
- **双读机制**：新 API 读取新字段，旧 API 继续使用旧字段。
- **灰度发布**：仅让部分用户/调用方切换到新版本。
- **逐步淘汰旧版本**：监控调用日志，确认旧 API 使用量降到安全范围后，再下线。

------

### 25.3 案例：用户 API 升级

**Before**

```
{
  "id": "123",
  "name": "Anna"
}
```

**After（灰度阶段）**

```
{
  "id": "123",
  "full_name": "Anna Wang",
  "name": "Anna"   // 保留旧字段，标记 Deprecated
}
```

- 应用逐步迁移到 `full_name`。
- 一段时间内同时支持 `name` 与 `full_name`。
- 监控发现 `name` 的调用方已全部迁移后，再删除。

------

### 小结

- **向后兼容**：新增字段安全，修改/删除危险。
- **灰度演进**：双写/双读 + 灰度发布 + 逐步淘汰。
- **核心思想**：API 重构应当渐进式、安全、可观测。

------

## 日本語版

### 序文

API は外部システムと内部システムを結ぶ **契約** です。
 破壊的な変更はクライアントにエラーを引き起こし、サービスの安定性を損ないます。
 したがって、API の **後方互換性** と **段階的ロールアウト（灰度リリース）** は大規模リファクタリングで必須の考慮点です。

------

### 25.1 後方互換性の原則

1. **追加は安全、削除・変更は危険**
   - 新しいフィールド追加は安全。削除やリネームは破壊的。
2. **デフォルト値・オプションパラメータの維持**
   - 古いクライアントでも新パラメータなしで動作可能にする。
3. **エラーコードの互換性**
   - 新コード追加は OK、既存コードの意味変更は NG。
4. **バージョニング**
   - `/api/v1` → `/api/v2` で破壊的変更を分離。

------

### 25.2 段階的ロールアウト（灰度リリース）

API 移行は一括切替が困難。
 👉 **戦略**：

- **二重書き込み**：新旧フィールド両方に保存。
- **二重読み取り**：新 API は新フィールドを利用、旧 API は旧フィールドを利用。
- **灰度リリース**：一部のユーザーだけ新バージョンを利用。
- **段階的廃止**：ログ監視で旧 API 利用がなくなったら削除。

------

### 25.3 事例：ユーザー API アップグレード

**Before**

```
{
  "id": "123",
  "name": "Anna"
}
```

**After（灰度段階）**

```
{
  "id": "123",
  "full_name": "Anna Wang",
  "name": "Anna"   // Deprecated
}
```

- アプリは徐々に `full_name` に移行。
- 一定期間 `name` と `full_name` を併存。
- 旧フィールド `name` の利用がなくなったら削除。

------

### まとめ

- **後方互換性**：追加は安全、変更や削除は危険。
- **灰度リリース**：二重書き込み・二重読み取り・段階的移行。
- **基本思想**：API リファクタリングは漸進的・安全・観測可能であるべき。

| 变更类型           | 示例                                  | 是否安全   | 灰度处理方式                                            |
| ------------------ | ------------------------------------- | ---------- | ------------------------------------------------------- |
| **新增字段**       | 在响应中增加 `email`                  | ✅ 安全     | 直接发布，客户端可选择忽略                              |
| **新增可选参数**   | 请求增加 `sortBy`（有默认值）         | ✅ 安全     | 提供默认值，旧客户端可不传                              |

| **字段删除**       | 删除 `phone`                          | ❌ 破坏性   | **先弃用** → 灰度发布 → 监控调用量 → 确认无人使用后删除 |
| **参数类型变更**   | `id: int → string`                    | ❌ 高风险   | **双写字段**（`id` 保留，新增 `idStr`），灰度迁移       |
| **默认值修改**     | 分页默认值从 10 → 50                  | ⚠️ 潜在破坏 | **分版本处理**，或在文档中明确升级指南                  |
| **新增错误码**     | 增加 `429 Too Many Requests`          | ✅ 安全     | 可直接发布，客户端应忽略未知错误码                      |
| **错误码语义改变** | `400` 含义改变（参数错误 → 权限错误） | ❌ 破坏性   | **新增错误码**，保留旧语义不变                          |

## 📊 Mermaid 流程图（中文版说明）

```
flowchart LR
    A[破坏性变更需求<br/>字段删除/重命名] --> B[新增字段/接口<br/>旧字段标记 Deprecated]
    B --> C[灰度发布<br/>新旧接口并存]
    C --> D[监控调用量<br/>日志/告警/埋点]
    D --> E{旧字段是否仍在使用?}
    E -->|是| C
    E -->|否| F[下线旧字段/接口<br/>彻底删除]
```

**说明（中文）：**

1. 遇到破坏性变更需求时，**先新增** 而不是直接修改/删除。
2. **灰度发布**：新旧接口并存，逐步迁移调用方。
3. **监控调用量**：确保旧接口的使用量逐渐下降到 0。
4. **最终删除**：确认无依赖后下线旧字段/接口。

## 📊 Mermaid フローチャート（日文版説明）

```
flowchart LR
    A[破壊的変更の要求<br/>フィールド削除・リネーム] --> B[新フィールド/新APIを追加<br/>旧フィールドは Deprecated]
    B --> C[段階的リリース<br/>新旧APIを併存]
    C --> D[利用状況を監視<br/>ログ・アラート・トラッキング]
    D --> E{旧フィールドはまだ利用中か?}
    E -->|はい| C
    E -->|いいえ| F[旧フィールド/APIを削除<br/>完全移行完了]
```

**説明（日文）：**

1. 破壊的変更が必要になったら、**直接変更せず新フィールド追加**。
2. **段階的リリース**：新旧 API を併存させ、徐々に移行。
3. **監視**：ログやメトリクスで旧 API の利用を追跡。
4. **削除**：依存がゼロになったら旧 API を削除し移行完了。
