## 第18回　条件 → 多态／策略模式

### 第18回　条件分岐から多態・ストラテジーパターンへ

------

## 中文版

### 引言

大量的 `if-else` 或 `switch` 语句，常常意味着程序中存在“类型判断”或“行为选择”。
 随着业务扩展，分支越来越多，代码可读性与可维护性逐渐恶化。

**解决方案**：

- **用多态替代条件**（Replace Conditional with Polymorphism）
- **用策略模式封装行为**（Strategy Pattern）

------

### 18.1 条件 → 多态

**示例（Before → After）**

```
// Before
fun shippingFee(type: String, weight: Int): Int {
    return when (type) {
        "EXPRESS" -> weight * 20
        "STANDARD" -> weight * 10
        "ECONOMY" -> weight * 5
        else -> 0
    }
}
// After：多态
interface Shipping {
    fun fee(weight: Int): Int
}

class Express : Shipping {
    override fun fee(weight: Int) = weight * 20
}
class Standard : Shipping {
    override fun fee(weight: Int) = weight * 10
}
class Economy : Shipping {
    override fun fee(weight: Int) = weight * 5
}

fun calcFee(s: Shipping, weight: Int) = s.fee(weight)
```

✅ 好处：新增类型时只需增加类，而不是修改 `when`。

------

### 18.2 条件 → 策略模式

**策略模式（Strategy Pattern）** 适合于：

- 行为可互换（如折扣算法、排序方式）。
- 条件判断逻辑经常变化。

**示例（Before → After）**

```
// Before
double discount(String type, double price) {
  if (type == "VIP") return price * 0.8;
  if (type == "REGULAR") return price * 0.9;
  return price;
}
// After：策略模式
abstract class DiscountStrategy {
  double apply(double price);
}

class VipDiscount implements DiscountStrategy {
  @override
  double apply(double price) => price * 0.8;
}

class RegularDiscount implements DiscountStrategy {
  @override
  double apply(double price) => price * 0.9;
}

class NoDiscount implements DiscountStrategy {
  @override
  double apply(double price) => price;
}

double discount(DiscountStrategy strategy, double price) {
  return strategy.apply(price);
}
```

✅ 好处：避免条件硬编码，新增/修改策略时对原代码影响最小。

------

### 18.3 适用场景总结

- **少量简单条件**：保留 `if/switch`，避免过度设计。
- **复杂条件、频繁扩展**：用 **多态** 或 **策略模式**。
- **跨多个模块的相似分支**：优先考虑模式化封装。

------

### 小结

- 条件分支过多 → 可读性差，扩展困难。
- 多态 & 策略模式 → 将条件转化为对象行为，降低耦合。
   **核心思想**：**让变化点独立、可扩展，而不是塞进条件判断。**

------

## 日本語版

### 序文

大量の `if-else` や `switch` 文は、プログラムに「型判定」や「挙動選択」が埋め込まれているサインです。
 ビジネス拡大とともに分岐が増え、可読性・保守性が低下します。

**解決策**：

- **条件分岐を多態に置換する**
- **戦略パターンで振る舞いをカプセル化する**

------

### 18.1 条件 → 多態

```
// Before
fun shippingFee(type: String, weight: Int): Int {
    return when (type) {
        "EXPRESS" -> weight * 20
        "STANDARD" -> weight * 10
        "ECONOMY" -> weight * 5
        else -> 0
    }
}
// After：多態
interface Shipping {
    fun fee(weight: Int): Int
}

class Express : Shipping {
    override fun fee(weight: Int) = weight * 20
}
class Standard : Shipping {
    override fun fee(weight: Int) = weight * 10
}
class Economy : Shipping {
    override fun fee(weight: Int) = weight * 5
}

fun calcFee(s: Shipping, weight: Int) = s.fee(weight)
```

✅ メリット：新しいタイプ追加時に `when` を修正する必要がない。

------

### 18.2 条件 → ストラテジーパターン

**ストラテジーパターン（Strategy Pattern）** は以下に適している：

- 振る舞いが差し替え可能（割引アルゴリズム、ソート方法など）。
- 条件判定ロジックが頻繁に変化する場合。

```
// Before
double discount(String type, double price) {
  if (type == "VIP") return price * 0.8;
  if (type == "REGULAR") return price * 0.9;
  return price;
}
// After：ストラテジーパターン
abstract class DiscountStrategy {
  double apply(double price);
}

class VipDiscount implements DiscountStrategy {
  @override
  double apply(double price) => price * 0.8;
}

class RegularDiscount implements DiscountStrategy {
  @override
  double apply(double price) => price * 0.9;
}

class NoDiscount implements DiscountStrategy {
  @override
  double apply(double price) => price;
}

double discount(DiscountStrategy strategy, double price) {
  return strategy.apply(price);
}
```

✅ メリット：条件分岐をなくし、新しい戦略追加が容易。

------

### 18.3 適用シナリオまとめ

- **少数の簡単な条件**：そのまま `if/switch` で十分。
- **複雑・拡張頻度高**：多態またはストラテジーパターンを適用。
- **複数モジュールに渡る分岐**：パターン化して整理。

------

### まとめ

- 条件分岐が多い → 可読性と拡張性が低下。
- 多態／ストラテジー → 条件をオブジェクト化し、疎結合で拡張可能に。
   **基本思想**：**変化点を条件に埋め込まず、オブジェクトに閉じ込めること。**
