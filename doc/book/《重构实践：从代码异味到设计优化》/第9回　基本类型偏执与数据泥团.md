## 第9回　基本类型偏执与数据泥团

### 第9回　基本型執着とデータの塊

------

## 中文版

### 引言

在类和方法的设计中，另两种常见的异味是：

- **基本类型偏执（Primitive Obsession）**
- **数据泥团（Data Clumps）**

它们看似无害，但会严重降低代码的语义清晰度与扩展性。

------

### 9.1 基本类型偏执（Primitive Obsession）

**特征**：

- 使用 `String`、`Int`、`Double` 等基本类型来表示复杂概念。
- 业务逻辑中充斥大量“裸值”，缺少明确约束。

**示例（Before → After）**

```
// Before
class User(val name: String, val email: String, val phone: String)

// Email、Phone 只是字符串，缺乏约束
val user = User("Anna", "invalid-email", "123")
// After：引入值对象（Value Object）
data class Email(val value: String) {
    init {
        require(value.contains("@")) { "Invalid email" }
    }
}
data class Phone(val value: String)

class User(val name: String, val email: Email, val phone: Phone)

val user = User("Anna", Email("anna@example.com"), Phone("080-1234-5678"))
```

✅ 好处：语义更明确，约束内聚到对象中，避免错误输入。

------

### 9.2 数据泥团（Data Clumps）

**特征**：

- 一组字段/参数总是同时出现。
- 它们本质上构成了一个“隐含的对象”，但没有被封装。

**示例（Before → After）**

```
// Before：重复传递 address 信息
void ship(String street, String city, String zip) {
  print("Shipping to $street, $city $zip");
}

void bill(String street, String city, String zip) {
  print("Billing to $street, $city $zip");
}
// After：引入 Address 类
class Address {
  final String street;
  final String city;
  final String zip;
  Address(this.street, this.city, this.zip);
}

void ship(Address address) {
  print("Shipping to ${address.street}, ${address.city} ${address.zip}");
}

void bill(Address address) {
  print("Billing to ${address.street}, ${address.city} ${address.zip}");
}
```

✅ 好处：减少重复，语义统一，扩展（如国家/地区字段）更容易。

------

### 9.3 两者的关系

- **基本类型偏执** → 缺少语义，导致逻辑分散、验证重复。
- **数据泥团** → 缺少封装，导致参数/字段重复出现。
   👉 本质都是“**没有对象化该对象应该承担的职责**”。

------

### 小结

- **基本类型偏执**：用值对象封装基本类型，让语义更明确。
- **数据泥团**：引入类，把总是一起出现的数据打包封装。
   **核心思想**：**让数据自己说话，让对象承担责任**。

## 日本語版

### 序文

クラスやメソッドの設計でよく見られる悪臭が：

- **基本型執着（Primitive Obsession）**
- **データの塊（Data Clumps）**

一見些細に見えても、コードの意味の明確さや拡張性を大きく損ないます。

------

### 9.1 基本型執着（Primitive Obsession）

**特徴**：

- `String`、`Int`、`Double` などの基本型で複雑な概念を表現。
- ビジネスロジックに「生の値」が散乱し、制約が欠如。

**例（Before → After）**

```
// Before
class User(val name: String, val email: String, val phone: String)

// Email、Phone は単なる文字列
val user = User("Anna", "invalid-email", "123")
// After：値オブジェクト導入
data class Email(val value: String) {
    init {
        require(value.contains("@")) { "Invalid email" }
    }
}
data class Phone(val value: String)

class User(val name: String, val email: Email, val phone: Phone)

val user = User("Anna", Email("anna@example.com"), Phone("080-1234-5678"))
```

✅ メリット：意味が明確になり、制約をオブジェクトに内包できる。

------

### 9.2 データの塊（Data Clumps）

**特徴**：

- 常にセットで現れるフィールドや引数群。
- 実際には「隠れたオブジェクト」だが、まだ封装されていない。

**例（Before → After）**

```
// Before：住所情報を毎回バラバラに渡す
void ship(String street, String city, String zip) {
  print("Shipping to $street, $city $zip");
}

void bill(String street, String city, String zip) {
  print("Billing to $street, $city $zip");
}
// After：Address クラスを導入
class Address {
  final String street;
  final String city;
  final String zip;
  Address(this.street, this.city, this.zip);
}

void ship(Address address) {
  print("Shipping to ${address.street}, ${address.city} ${address.zip}");
}

void bill(Address address) {
  print("Billing to ${address.street}, ${address.city} ${address.zip}");
}
```

✅ メリット：重複を減らし、意味を統一し、拡張もしやすい。

------

### 9.3 両者の関係

- **基本型執着** → 意味が不明確になり、ロジックが分散する。
- **データの塊** → カプセル化不足で、同じ引数やフィールドが繰り返される。
   👉 共通点は「**本来オブジェクトにすべき責務をオブジェクト化していない**」こと。

------

### まとめ

- **基本型執着**：値オブジェクトで基本型をラップし、意味を明確化。
- **データの塊**：クラスを導入して一緒に現れるデータをカプセル化。
   **基本理念**：**データに責任を持たせ、オブジェクトに語らせること。**
