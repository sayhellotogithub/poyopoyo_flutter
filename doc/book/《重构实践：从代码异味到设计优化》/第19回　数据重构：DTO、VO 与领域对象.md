## 第19回　数据重构：DTO、VO 与领域对象

### 第19回　データリファクタリング：DTO・VO・ドメインオブジェクト

------

## 中文版

### 引言

在重构实践中，除了方法与类的调整外，**数据的设计与建模** 同样重要。
 许多系统的复杂度往往源于“数据表示混乱”，常见问题包括：

- 在网络传输、存储、业务逻辑中使用相同的数据结构。
- 过度依赖基本类型（字符串、数字）来表达复杂数据。
- 缺乏明确的数据边界，职责混乱。

因此，数据重构的关键在于：**合理区分 DTO、VO 与领域对象**。

------

### 19.1 DTO（Data Transfer Object）

**定义**：用于 **跨层传输数据** 的对象，通常是轻量级的，不包含业务逻辑。
 **特征**：

- 字段常与数据库表或接口 JSON 一一对应。
- 只作为“数据搬运工”。
- 在接口层、DAO 层使用。

**示例**：

```
// DTO：与 API 请求/响应对应
data class UserDto(
    val id: String,
    val name: String,
    val email: String
)
```

------

### 19.2 VO（Value Object 值对象）

**定义**：用于表示一个有明确语义的值，**不可变**，通过值比较相等性。
 **特征**：

- 表示领域中的概念（如 Email、Money）。
- 内部可包含验证逻辑。
- 常在领域模型中使用。

**示例**：

```
data class Email(val value: String) {
    init {
        require(value.contains("@")) { "Invalid email" }
    }
}
```

------

### 19.3 领域对象（Domain Object / Entity）

**定义**：核心业务逻辑的载体，封装行为与数据，通常有唯一标识符。
 **特征**：

- 表示领域中的实体（如 User、Order）。
- 负责业务规则与状态变更。
- 有生命周期，通常存在 ID。

**示例**：

```
data class UserId(val value: String)

class User(val id: UserId, var name: String, var email: Email) {
    fun changeEmail(newEmail: Email) {
        this.email = newEmail
    }
}
```

------

### 19.4 三者关系与重构思路

- **DTO**：面向数据传输，避免业务逻辑污染。
- **VO**：用来表达领域中的值概念，增加语义清晰度。
- **领域对象**：承载核心业务逻辑。

👉 重构方向：

- 不要在业务逻辑中直接使用 DTO。
- 遇到“基本类型偏执”时，引入 VO。
- 将业务行为放入领域对象，而不是服务类或控制器中。

------

### 小结

- **DTO**：数据搬运工，跨层传输用。
- **VO**：不可变值对象，增加语义与约束。
- **领域对象**：业务逻辑核心，封装数据与行为。

**核心思想**：通过合理的数据建模，让代码 **语义明确、职责清晰、演进容易**。

------

## 日本語版

### 序文

リファクタリングでは、メソッドやクラスの改善だけでなく、**データの設計とモデリング** も極めて重要です。
 多くのシステムは「データ表現の混乱」から複雑化します。典型的な問題は：

- ネットワーク伝送・保存・業務ロジックに同じデータ構造を使う。
- 基本型（文字列・数値）で複雑な概念を表現する。
- データの境界が曖昧で責務が混乱する。

解決の鍵は：**DTO・VO・ドメインオブジェクトを明確に区別すること**。

------

### 19.1 DTO（Data Transfer Object）

**定義**：**レイヤー間のデータ伝送** に使う軽量オブジェクト。業務ロジックは持たない。
 **特徴**：

- フィールドは DB テーブルや API JSON と一対一対応。
- 「データの運び屋」。
- インタフェース層・DAO 層で利用。

```
// DTO：API リクエスト／レスポンスに対応
data class UserDto(
    val id: String,
    val name: String,
    val email: String
)
```

------

### 19.2 VO（Value Object 値オブジェクト）

**定義**：意味を持つ値を表現する **不変オブジェクト**。値の比較で等価性を判断。
 **特徴**：

- ドメイン内の概念（Email、Money など）を表現。
- 内部にバリデーションを持つ場合がある。
- ドメインモデルで利用される。

```
data class Email(val value: String) {
    init {
        require(value.contains("@")) { "Invalid email" }
    }
}
```

------

### 19.3 ドメインオブジェクト（Domain Object / Entity）

**定義**：業務ロジックの中心を担う。データと振る舞いをカプセル化し、一意な ID を持つ。
 **特徴**：

- ドメイン上の実体（User、Order など）を表現。
- 業務ルール・状態遷移を担う。
- ライフサイクルを持ち、通常は ID を持つ。

```
data class UserId(val value: String)

class User(val id: UserId, var name: String, var email: Email) {
    fun changeEmail(newEmail: Email) {
        this.email = newEmail
    }
}
```

------

### 19.4 三者の関係とリファクタリング方針

- **DTO**：データ伝送用、業務ロジックを含めない。
- **VO**：値の概念を表現し、意味を明確化。
- **ドメインオブジェクト**：業務ロジックを担う中核。

👉 リファクタリング方針：

- ビジネスロジックで DTO を直接使わない。
- 基本型執着が見られる場合は VO を導入。
- 業務の振る舞いはサービスやコントローラではなく、ドメインオブジェクトに置く。

------

### まとめ

- **DTO**：レイヤー間のデータ搬送。
- **VO**：不変値オブジェクト、意味と制約を付与。
- **ドメインオブジェクト**：業務ロジックの中核。

**基本思想**：データモデリングを明確にすることで、コードは **意味が明確で責務が整理され、進化に耐えられる**。
