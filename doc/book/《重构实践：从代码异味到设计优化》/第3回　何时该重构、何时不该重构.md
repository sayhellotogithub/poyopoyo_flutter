## 第3回　何时该重构、何时不该重构

### 第3回　いつリファクタリングすべきか、すべきでないか

------

## 中文版

### 引言

重构是改善代码质量的有力手段，但并不是在任何时候都适合。
 如果时机错误，重构可能会变成“浪费时间”甚至“埋下隐患”。
 因此，开发者需要清楚地判断：**什么时候该重构，什么时候不该重构**。

------

### 3.1 何时该重构 ✅

- **代码异味明显**：
   出现重复代码、长函数、巨型类、复杂条件等情况。
- **需求变更前**：
   先重构，让代码更容易接受新的修改。
- **修复 Bug 前**：
   通过小重构让逻辑清晰，再更安全地修复。
- **代码审查反馈后**：
   Reviewer 指出结构混乱时，及时调整。
- **日常工作中顺手**：
   Boy Scout Rule —— 每次提交时让代码变得更好一点。

------

### 3.2 何时不该重构 ❌

- **功能尚未实现时**：
   还没有完整逻辑就开始“优化”，其实是过早设计。
- **缺乏测试保障时**：
   没有自动化测试的情况下大规模重构，风险极高。
- **临近发布截止时**：
   紧急上线时应优先保证交付，重构可延后。
- **仅为个人偏好时**：
   风格不同不是重构的理由，应以团队共识为准。
- **收益小于成本时**：
   如果改动带来风险，却几乎没有实际收益，可以暂缓。

------

### 3.3 案例对比

**正例：**
 在实现新功能前，发现原有函数过长、难以扩展 → 提取函数、拆分类，再开发新功能。
 👉 好处：新功能可以自然融入，Bug 风险更低。

**反例：**
 产品上线前一天，为了“看起来更优雅”大改结构 → 没有测试保障 → 发布后出现回归 Bug。
 👉 结果：得不偿失。

------

### 小结

> **重构的关键在于时机。**

- 合适的时机：在异味出现、变更之前、修复之前。
- 不合适的时机：在缺乏测试、临近上线、仅凭个人喜好时。

重构是一项投资，**要在收益大于风险时进行**。

## 日本語版

### 序文

リファクタリングはコード品質を改善する有効な手段ですが、**いつでも適切とは限りません**。
 タイミングを誤ると「時間の浪費」や「新たな不具合の温床」になりかねません。
 開発者は **リファクタリングすべき時と、すべきでない時** を明確に判断する必要があります。

------

### 3.1 リファクタリングすべき時 ✅

- **コードの悪臭が明確なとき**：
   重複コード、長すぎるメソッド、巨大クラス、複雑な条件式など。
- **要件変更の前**：
   変更に耐えられるよう、まず構造を整える。
- **バグ修正の前**：
   ロジックを整理してから修正することで、安全性が高まる。
- **コードレビューで指摘を受けたとき**：
   構造が不明瞭だと指摘されたら、早めに改善。
- **日常作業のついでに**：
   ボーイスカウトルール —— 「触れたコードは必ず良くしてから戻す」。

------

### 3.2 リファクタリングすべきでない時 ❌

- **機能がまだ未完成のとき**：
   ロジックが固まっていない段階での「最適化」は過剰設計になりやすい。
- **テストが不足しているとき**：
   自動テストなしで大規模リファクタリングはリスクが高すぎる。
- **リリース直前のとき**：
   納期優先。リファクタリングは後回しにする。
- **単なる個人の好みの場合**：
   スタイルの違いは理由にならない。チームの合意が必要。
- **コスト＞効果のとき**：
   改善による利益が小さいなら、優先度を下げる。

------

### 3.3 ケース比較

**良い例：**
 新機能を追加する前に、既存の長すぎるメソッドを分割しておく。
 👉 メリット：新機能をスムーズに統合でき、バグも減る。

**悪い例：**
 リリース前日に「きれいに見せたい」からと構造を大幅に改変 → テスト不足 → 本番で不具合発生。
 👉 デメリット：完全に逆効果。

------

### まとめ

> **リファクタリングの肝はタイミングにある。**

- 適切なタイミング：悪臭が出た時、変更や修正の前。
- 不適切なタイミング：テストがない時、リリース直前、個人の好みで動く時。

リファクタリングは投資であり、**効果がコストを上回る時に行うのがベスト**。
