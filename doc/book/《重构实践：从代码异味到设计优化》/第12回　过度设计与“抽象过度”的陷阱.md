## 第12回　过度设计与“抽象过度”的陷阱

### 第12回　過剰設計と「抽象のやりすぎ」の落とし穴

------

## 中文版

### 引言

如果说“代码异味”常常来自**缺乏设计**，那么另一种常见问题则来自**过度设计**。
 开发者往往为了“未来可能的需求”提前设计大量抽象层，却导致：

- 代码复杂度急剧上升。
- 维护者理解困难。
- 新功能反而难以快速实现。

这就是所谓的 **抽象过度（Speculative Generality）**。

------

### 12.1 过度设计的典型特征

- 接口/抽象类只有一个实现。
- 为“将来可能的需求”提前设计复杂的继承结构。
- 工厂模式、策略模式被滥用，却没有真正的扩展需求。
- 代码充斥“预留参数”“未使用的扩展点”。

------

### 12.2 示例（Before → After）

```
// Before：过度抽象
interface PaymentProcessor {
    fun process(amount: Double)
}

class CreditCardProcessor : PaymentProcessor {
    override fun process(amount: Double) {
        println("Paid $amount with credit card")
    }
}

// 实际只有一个实现，接口多余
fun main() {
    val processor: PaymentProcessor = CreditCardProcessor()
    processor.process(100.0)
}
// After：去掉多余抽象
class CreditCardProcessor {
    fun process(amount: Double) {
        println("Paid $amount with credit card")
    }
}

fun main() {
    val processor = CreditCardProcessor()
    processor.process(100.0)
}
```

✅ 好处：代码简洁，不会让维护者困惑。

------

### 12.3 何时需要抽象，何时应避免？

- **需要抽象**：当系统中确实有多个实现，或者未来扩展是确定需求。
- **避免抽象**：当只有一个实现，或者“未来也许会有”的需求并不确定。

**一句口诀**：

> **YAGNI（You Ain’t Gonna Need It）—— 你不会真的需要它。**

------

### 小结

- **过度设计** 是另一种异味：代码看似灵活，却让维护和理解变得更难。
- **解决办法**：删除无用抽象，按需设计，遵循 YAGNI 原则。
   **核心思想**：设计要恰到好处，而不是越多越好。

------

## 日本語版

### 序文

「コードの悪臭」がしばしば **設計不足** から生じる一方で、逆に **過剰な設計** も問題を引き起こします。
 開発者が「将来必要になるかもしれない」と考えて抽象を追加すると：

- コードの複雑さが急増。
- メンテナンスが困難に。
- 新機能の追加が遅くなる。

これが **過剰設計（Speculative Generality／抽象のやりすぎ）** です。

------

### 12.1 過剰設計の典型的な特徴

- インタフェース／抽象クラスに実装が1つしかない。
- 「将来のため」に複雑な継承階層を用意している。
- ファクトリーやストラテジーパターンを乱用しているが、拡張の必然性がない。
- 使われない引数や拡張ポイントがコードに散在している。

------

### 12.2 例（Before → After）

```
// Before：過剰な抽象
interface PaymentProcessor {
    fun process(amount: Double)
}

class CreditCardProcessor : PaymentProcessor {
    override fun process(amount: Double) {
        println("Paid $amount with credit card")
    }
}

fun main() {
    val processor: PaymentProcessor = CreditCardProcessor()
    processor.process(100.0)
}
// After：不要な抽象を削除
class CreditCardProcessor {
    fun process(amount: Double) {
        println("Paid $amount with credit card")
    }
}

fun main() {
    val processor = CreditCardProcessor()
    processor.process(100.0)
}
```

✅ メリット：コードが簡潔になり、保守者が迷わなくなる。

------

### 12.3 抽象を導入すべきか？避けるべきか？

- **導入すべき**：複数の実装が存在する、または拡張が確実に必要な場合。
- **避けるべき**：実装が1つしかなく、「将来使うかも」程度の不確実なニーズしかない場合。

**合言葉**：

> **YAGNI（You Ain’t Gonna Need It）—— どうせ必要にならない。**

------

### まとめ

- **過剰設計** は「柔軟に見えて実は足かせ」になる悪臭。
- **解決策**：不要な抽象を削除し、必要に応じてだけ設計する。
   **基本思想**：設計は「ちょうどよさ」が大事で、多ければ多いほど良いわけではない。
