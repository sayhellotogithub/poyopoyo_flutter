## 第20回　API 兼容性与版本化

### 第20回　API互換性とバージョニング

------

## 中文版

### 引言

在真实系统中，**API 是契约**。
 一旦 API 被外部依赖，就意味着：

- 内部实现可以重构，但外部接口不能轻易改变。
- 改动 API 会导致客户端/调用方崩溃。

因此，在进行重构时，API 的 **兼容性与版本化** 是必须考虑的问题。

------

### 20.1 API 兼容性（Compatibility）

**保持兼容性的做法**：

- **新增字段而不是删除字段**
  - 请求/响应体中避免直接删除已有字段。
- **保持参数默认值**
  - 新增参数时，给出默认值以保证旧调用不受影响。
- **非破坏性变更优先**
  - 添加功能 → ✅
  - 删除/修改已有字段 → ❌

**示例**：

```
// Before
{
  "id": "123",
  "name": "Anna"
}

// After（兼容）
{
  "id": "123",
  "name": "Anna",
  "email": "anna@example.com"  // 新增字段
}
```

------

### 20.2 API 版本化（Versioning）

当变更不可避免时，应通过版本化来隔离。

常见版本化策略：

1. **URL 版本化**
   - `/api/v1/users` → `/api/v2/users`
   - 简单直观，但 URL 会膨胀。
2. **Header 版本化**
   - `Accept: application/vnd.myapp.v2+json`
   - REST 社区常用，灵活但需要客户端支持。
3. **参数版本化**
   - `/api/users?version=2`
   - 简单，但容易混乱。

👉 最佳实践：**主要 API 使用 URL 版本化**，同时结合 Header 表示功能特性。

------

### 20.3 向后兼容的重构策略

- **适配层（Adapter Layer）**：保留旧接口，内部转发到新实现。
- **弃用标记（Deprecation Notice）**：明确告诉调用方旧版本将被淘汰。
- **渐进迁移**：一段时间内同时支持 v1 和 v2。

------

### 小结

- **API 是契约**：内部可重构，外部需保持稳定。
- **兼容性优先**：新增而非删除，默认值保障老版本。
- **版本化机制**：用 v1/v2 管理不可避免的破坏性变更。
   **核心思想**：在演进中保持稳定，重构与可用性两者兼得。

------

## 日本語版

### 序文

実際のシステムにおいて、**API は契約** です。
 API が外部から利用されている以上：

- 内部実装はリファクタリング可能だが、外部インタフェースは安易に変更できない。
- API を変更するとクライアント／呼び出し元が壊れる可能性がある。

したがって、リファクタリングの際には **API の互換性とバージョニング** を考慮する必要があります。

------

### 20.1 API互換性（Compatibility）

**互換性を保つ方法**：

- **削除せず追加**
  - リクエスト／レスポンスの既存フィールドを削除しない。
- **デフォルト値を保持**
  - 新しいパラメータを追加する場合、デフォルト値を設定し旧呼び出しを壊さない。
- **非破壊的変更を優先**
  - 機能追加 → ✅
  - 既存フィールドの削除／変更 → ❌

```
// Before
{
  "id": "123",
  "name": "Anna"
}

// After（互換性あり）
{
  "id": "123",
  "name": "Anna",
  "email": "anna@example.com"
}
```

------

### 20.2 APIバージョニング（Versioning）

避けられない変更はバージョン管理で分離する。

代表的な方法：

1. **URL バージョニング**
   - `/api/v1/users` → `/api/v2/users`
   - シンプルだが URL が肥大化する。
2. **Header バージョニング**
   - `Accept: application/vnd.myapp.v2+json`
   - REST でよく使われる。柔軟だがクライアント対応が必要。
3. **クエリパラメータ**
   - `/api/users?version=2`
   - 簡単だが混乱しやすい。

👉 ベストプラクティス：**基本は URL バージョニング**、機能差分は Header で表現。

------

### 20.3 後方互換性を意識したリファクタリング戦略

- **アダプタ層**：旧 API を残しつつ内部で新実装に委譲。
- **非推奨マーク**：旧バージョン廃止予定を明示。
- **段階的移行**：一定期間 v1 と v2 を並行稼働させる。

------

### まとめ

- **API は契約**：内部リファクタリングは自由だが外部安定性が必須。
- **互換性優先**：追加は OK、削除や変更は NG。
- **バージョニング**：破壊的変更は v1/v2 で管理。
   **基本思想**：進化と安定性の両立。

# 📑 附录：API 变更对照表（中文版）

| 变更类型                  | 示例                                | 是否安全   | 建议做法                             |
| ------------------------- | ----------------------------------- | ---------- | ------------------------------------ |
| **新增字段**（请求/响应） | 响应 JSON 中多一个 `email` 字段     | ✅ 安全     | 保持旧字段不变，客户端可忽略新字段   |
| **新增可选参数**          | API 增加 `sortBy` 参数（有默认值）  | ✅ 安全     | 提供默认值，保证旧调用继续有效       |
| **字段重命名**            | `userName` → `name`                 | ❌ 破坏性   | 保留旧字段，增加新字段，逐步弃用     |
| **字段删除**              | 删除 `phone` 字段                   | ❌ 破坏性   | 使用版本化（v2），或提供兼容层       |
| **参数类型变更**          | `id` 从 `int` 改为 `string`         | ❌ 高风险   | 保持旧参数，新增新字段（如 `idStr`） |
| **默认值修改**            | 默认分页大小从 10 → 50              | ⚠️ 潜在破坏 | 明确文档，必要时通过版本化处理       |
| **错误码新增**            | 增加 `429 Too Many Requests`        | ✅ 安全     | 客户端可忽略未知错误码               |
| **错误码语义改变**        | `400` 原本是参数错误 → 改成权限错误 | ❌ 破坏性   | 引入新的错误码，保持旧码含义不变     |
