## 第28回　从条件语句到策略模式

### 第28回　条件分岐からストラテジーパターンへ

------

## 中文版

### 背景

在实际业务代码中，复杂的 `if-else` 或 `switch` 语句很常见：

- 根据不同用户类型决定折扣方式。
- 根据不同文件类型决定解析逻辑。
- 根据不同支付方式调用不同网关。

随着分支增多，代码逐渐变得：

- 可读性差。
- 难以扩展（新增一种分支就要改 if/switch）。
- 容易遗漏逻辑。

👉 **策略模式**（Strategy Pattern）是替代复杂条件语句的常用重构手法。

------

### 28.1 条件语句的问题

```
public double discount(String type, double price) {
    if (type.equals("VIP")) {
        return price * 0.8;
    } else if (type.equals("REGULAR")) {
        return price * 0.9;
    } else {
        return price;
    }
}
```

缺点：

- `if-else` 越来越多时，可读性和维护性下降。
- 扩展需要修改原方法，不符合 **开闭原则**。

------

### 28.2 策略模式重构

```
// 策略接口
interface DiscountStrategy {
    double apply(double price);
}

// 具体策略
class VipDiscount implements DiscountStrategy {
    public double apply(double price) { return price * 0.8; }
}

class RegularDiscount implements DiscountStrategy {
    public double apply(double price) { return price * 0.9; }
}

class NoDiscount implements DiscountStrategy {
    public double apply(double price) { return price; }
}

// 上下文
class DiscountContext {
    private final DiscountStrategy strategy;
    public DiscountContext(DiscountStrategy strategy) {
        this.strategy = strategy;
    }
    public double getPrice(double price) {
        return strategy.apply(price);
    }
}
```

使用方式：

```
DiscountContext ctx = new DiscountContext(new VipDiscount());
System.out.println(ctx.getPrice(100));  // 80.0
```

✅ 好处：

- 新增一种折扣方式时，只需新增一个策略类。
- 原有代码无需修改，符合开闭原则。
- 策略可以复用、组合，甚至动态切换。

------

### 28.3 适用场景

- 条件逻辑对应 **可互换的算法/行为**。
- 新增分支的可能性较高。
- 逻辑经常需要单独测试或复用。

不适合：

- 分支非常少、逻辑简单的场景（过度设计）。

------

### 小结

- 条件语句过多时，代码难以维护。
- 策略模式通过 **接口+实现类** 将条件分支转化为可扩展的对象。
- 本质是：**用组合替代条件判断，用多态实现扩展性**。

------

## 日本語版

### はじめに

実際の業務コードでは、複雑な `if-else` や `switch` 文が頻繁に登場する：

- ユーザー種別ごとの割引計算。
- ファイル種別ごとの解析処理。
- 決済方法ごとのゲートウェイ呼び出し。

分岐が増えると：

- 可読性が下がる。
- 新しい分岐を追加するたびに if/switch を修正する必要がある。
- ロジック抜けが発生しやすい。

👉 **ストラテジーパターン** は、このような条件分岐を整理する有効なリファクタリング手法である。

------

### 28.1 条件分岐の問題点

```
public double discount(String type, double price) {
    if (type.equals("VIP")) {
        return price * 0.8;
    } else if (type.equals("REGULAR")) {
        return price * 0.9;
    } else {
        return price;
    }
}
```

問題点：

- `if-else` が増えると可読性・保守性が低下。
- 新しい分岐を追加するたびに元コードを変更する必要があり、**オープン・クローズド原則**に反する。

------

### 28.2 ストラテジーパターンによるリファクタリング

```
// 戦略インタフェース
interface DiscountStrategy {
    double apply(double price);
}

// 具体戦略
class VipDiscount implements DiscountStrategy {
    public double apply(double price) { return price * 0.8; }
}

class RegularDiscount implements DiscountStrategy {
    public double apply(double price) { return price * 0.9; }
}

class NoDiscount implements DiscountStrategy {
    public double apply(double price) { return price; }
}

// コンテキスト
class DiscountContext {
    private final DiscountStrategy strategy;
    public DiscountContext(DiscountStrategy strategy) {
        this.strategy = strategy;
    }
    public double getPrice(double price) {
        return strategy.apply(price);
    }
}
```

利用例：

```
DiscountContext ctx = new DiscountContext(new VipDiscount());
System.out.println(ctx.getPrice(100));  // 80.0
```

✅ メリット：

- 新しい割引方式を追加する場合、新しいクラスを作るだけで良い。
- 既存コードを修正せずに拡張可能。
- 戦略は再利用・組み合わせ・動的切替が可能。

------

### 28.3 適用シナリオ

- 条件分岐が **切り替え可能なアルゴリズム／挙動** に対応している場合。
- 分岐の追加が頻繁に発生する場合。
- ロジックを個別にテスト・再利用したい場合。

不適切な場合：

- 分岐が少なく、ロジックが単純な場合（過剰設計になる）。

------

### まとめ

- 条件分岐が多いコードは可読性と保守性を下げる。
- ストラテジーパターンは、条件を **オブジェクトに置き換え**、拡張性を高める。
- 本質は **条件判断を排除し、ポリモーフィズムと組み合わせで柔軟にすること**。

# 📑 条件语句 → 重构手法对照表（中文版）

| 条件语句问题             | 典型症状                    | 重构手法                                                  | 示例场景                           |
| ------------------------ | --------------------------- | --------------------------------------------------------- | ---------------------------------- |
| **条件过长**             | `if (a && b                 |                                                           | c)` 嵌套层级深                     |
| **复杂条件下的早退出**   | 方法内部层层嵌套 `if`       | **卫语句（Guard Clauses）**                               | 参数为空 → 直接 `return`，减少嵌套 |
| **分支逻辑不同但可抽象** | 多个 `if-else` 选择不同算法 | **策略模式（Strategy Pattern）**                          | 折扣计算、排序策略、日志写入策略   |
| **分支逻辑基于对象类型** | `if (type == "VIP")`        | **多态替代条件（Replace Conditional with Polymorphism）** | User 子类自己决定折扣算法          |

👉 总结：

- **条件分解/卫语句** → 解决方法内部逻辑清晰度问题。
- **策略模式/多态** → 解决分支可扩展性问题。

------

# 📑 条件分岐 → リファクタリング手法対応表（日文版）

| 条件分岐の問題                   | 典型的な症状           | リファクタリング手法                                         | 例                                 |
| -------------------------------- | ---------------------- | ------------------------------------------------------------ | ---------------------------------- |
| **条件が長い**                   | `if (a && b            |                                                              | c)` が複雑                         |
| **入れ子が深い**                 | `if` が階層的に増える  | **ガード節（Guard Clauses）**                                | パラメータ不正なら早期 `return`    |
| **分岐ごとに異なるアルゴリズム** | `if-else` で処理が切替 | **ストラテジーパターン（Strategy Pattern）**                 | 割引計算、ソート方法、ログ出力戦略 |
| **型や種別で条件分岐**           | `if (type == "VIP")`   | **ポリモーフィズムに置換（Replace Conditional with Polymorphism）** | User サブクラスが自分で割引を計算  |

👉 まとめ：

- **条件式分解・ガード節** → メソッド内部の可読性改善。
- **ストラテジー・ポリモーフィズム** → 分岐拡張性の改善。
