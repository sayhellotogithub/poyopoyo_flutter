## 第4回　重构的流程：小步快跑 + 自动化测试

### 第4回　リファクタリングのプロセス：小さなステップと自動テスト

------

## 中文版

### 引言

重构不是一次“大手术”，而更像是一场**持续的小清理**。
 要想在不破坏现有功能的前提下改善代码，我们需要遵循一套**安全的流程**：小步快跑、随时回退、自动化测试保驾护航。

------

### 4.1 为什么要小步快跑

- **降低风险**：一次只修改很小一部分，错误容易定位。
- **随时可回滚**：每一步都能编译通过、测试通过，可以安全提交。
- **保持节奏**：避免“重构半个月，功能全停摆”的情况。

#### 实践建议

- 每次修改 **不超过 10 行核心逻辑**。
- 修改后立即运行测试并提交。
- 保持 Git commit 粒度小且语义清晰，例如：
  - `refactor: extract method for tax calculation`
  - `refactor: introduce parameter object in schedule API`

------

### 4.2 自动化测试是安全网

- **保障行为不变**：测试通过意味着功能未被破坏。
- **提升信心**：敢于大幅度调整结构，而不用担心引入隐性 Bug。
- **加速迭代**：避免手工测试的低效与遗漏。

#### 测试重点

- **单元测试**：覆盖核心业务逻辑。
- **集成测试**：验证模块之间的交互是否仍然正确。
- **回归测试**：确保既有功能不受影响。

------

### 4.3 一个典型的重构循环

1. **准备**：确认已有自动化测试；若缺失，先补关键路径测试。
2. **小步修改**：应用一个具体手法（如 Extract Method）。
3. **运行测试**：必须全部通过。
4. **提交代码**：小步提交，保证可回滚。
5. **重复循环**：继续下一个小重构。

------

### 4.4 可视化流程（Mermaid）

```
flowchart LR
  A[准备：测试覆盖] --> B[小步修改]
  B --> C[运行自动化测试]
  C -->|通过| D[提交代码]
  C -->|失败| B
  D --> E[进入下一步重构]
```

------

### 小结

> **重构不是一蹴而就，而是一系列小而安全的改进。**
>  小步快跑让重构风险可控，自动化测试让改进更有信心。
>  在团队协作中，这种节奏更能保持开发与交付的平衡。

## 日本語版

### 序文

リファクタリングは「大手術」ではなく、**継続的な小さな掃除**に近いものです。
 既存の機能を壊さずにコードを改善するためには、**小さなステップ**と**自動テスト**を組み合わせた安全なプロセスが必要です。

------

### 4.1 なぜ小さなステップなのか

- **リスク低減**：一度に少しだけ変更するので、バグがあっても特定しやすい。
- **即時ロールバック可能**：各ステップはコンパイル可能・テスト合格状態でコミットできる。
- **開発リズムを維持**：長期間の「リファクタリング停滞」を避ける。

#### 実践ポイント

- 1回の変更は **10行程度のロジック以内** に抑える。
- 変更後すぐテストを実行し、コミットする。
- Git コミットは小粒度で意味を明確に：
  - `refactor: 税計算をメソッド抽出`
  - `refactor: schedule API にパラメータオブジェクト導入`

------

### 4.2 自動テストは安全ネット

- **振る舞いを保証**：テストが通れば機能が壊れていないことを確認できる。
- **安心感の向上**：大胆な構造変更も安心して行える。
- **開発効率向上**：手動テストの手間や漏れを防ぐ。

#### テストの重点

- **ユニットテスト**：ビジネスロジックのコアをカバー。
- **統合テスト**：モジュール間のやり取りを確認。
- **回帰テスト**：既存機能への影響を検出。

------

### 4.3 典型的なリファクタリングサイクル

1. **準備**：自動テストの有無を確認。なければ重要部分を補完。
2. **小さな変更**：具体的な手法（例：メソッド抽出）を適用。
3. **テスト実行**：全てパスすることを確認。
4. **コミット**：小さく区切り、ロールバック可能にする。
5. **ループ継続**：次のリファクタリングへ。

------

### 4.4 プロセスの図解（Mermaid）

```
flowchart LR
  A[準備：テストカバレッジ] --> B[小さな変更]
  B --> C[自動テスト実行]
  C -->|合格| D[コミット]
  C -->|失敗| B
  D --> E[次のリファクタリングへ]
```

------

### まとめ

> **リファクタリングは一度きりの行為ではなく、安全な小改良の積み重ねである。**
>  小さなステップがリスクを抑え、自動テストが安心感を支える。
>  チーム開発においても、このリズムが「改善と納品の両立」を実現する。
