### 一、整体架构风格趋势

#### 推荐的主流架构风格

| 架构风格                               | 说明                                                        |
| -------------------------------------- | ----------------------------------------------------------- |
| **Clean Architecture**                 | 按照“领域驱动设计”思想，分层明确，利于大型团队协作。        |
| **MVVM + Riverpod**                    | 搭配 `Riverpod` 来实现 ViewModel 层，解耦 UI 与业务逻辑。   |
| **DDD-lite + Feature-based + Modular** | 按“功能模块”拆分项目结构，搭配轻量的领域建模（非严谨DDD）。 |
| **Flutter Modular/GoRouter**           | 路由解耦，配合依赖注入方案支持动态模块加载。                |

### 二、主流 Flutter 项目的文件夹结构（Feature-first + Clean）

```
lib/
│
├── core/               # 共通逻辑（网络、缓存、样式等）
│   ├── network/
│   ├── theme/
│   └── utils/
│
├── features/           # 按功能拆分模块
│   ├── auth/
│   │   ├── data/
│   │   ├── domain/
│   │   ├── presentation/
│   │   └── auth_route.dart
│   └── weather/
│       ├── data/
│       ├── domain/
│       └── presentation/
│
├── services/           # 通用的跨 feature 的服务类
│
├── l10n/               # 多语言支持
├── app.dart            # App 入口定义，包含路由/主题初始化
└── main.dart           # 启动入口

```

### 三、主要技术栈组合（推荐）

| 层级           | 推荐技术                                                     |
| -------------- | ------------------------------------------------------------ |
| **UI层**       | Flutter（基本Widgets + CustomPainter + Animations）          |
| **状态管理**   | Riverpod（推荐 `hooks_riverpod` / `flutter_riverpod`）也有团队用 bloc/cubit 或 GetX，但在大型项目中 Riverpod 更可维护 |
| **路由管理**   | `go_router`（推荐），或使用 `auto_route`                     |
| **依赖注入**   | `riverpod` 自带 Provider 机制，或使用 `get_it`（在非Riverpod项目中） |
| **数据访问层** | Dio + Freezed + Retrofit（或 Chopper）                       |
| **本地数据库** | Drift 或 Isar（比 sqflite 更现代）                           |
| **模型转换**   | `freezed` + `json_serializable`（推荐组合）                  |
| **测试**       | `flutter_test` + `mocktail`/`mockito` + `integration_test`   |
| **构建工具**   | `mason`（用于代码模板生成）、`melos`（用于多包管理）         |
